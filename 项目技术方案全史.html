总览

项目由一个需求驱动：真实摔倒照片太少（252 张无法支撑训练），需要合成大量「真实可标注」的摔倒视频。合成数据不落地、人物漂移、标注不可用，都是这个需求路上的拦路虎。

方案矩阵（含废案与原因链）

⓪ 摔倒仿真早期（Codex 时代 · 六次改道）—— 被历史验证的"没必要"

在 H3 之前，摔倒仿真已经走过六条完全不同的路；每一段都有可量化的验收数据，且全部因"效果或原理"被推翻。这段历史证明了最终 H3 首帧方案为何是收敛点。

废案

MuJoCo 胶囊人偶物理（v0.10.39-44）

物理仿真 + 三视图离屏渲染自动出框。真实背景合成，fall_mixed 训练：真实照片 person 12/12、倒地 10/10，val mAP50=0.98。

放弃：用户明确"不要方块人"——物理是对的，但"胶囊人偶"永远不像真人；整套（含 MuJoCo 依赖/模型/合成器）全删（v0.11.0）。
废案

真人像素合成（2D 元素库 · v0.11.0）

yolo11n-seg 从真照片抠出 193 个真人元素 + inpaint 车间背景库，随机组合。留出 20 张真图：fall mAP50=0.995 / R=1.0（全场最佳精度）。

为什么又放弃：精度封顶但"合成痕迹"仍在（人物贴片感、光影不融合）；且只有平面变换，无法应对真实三维视角。它作为精度基准被后两代参照。
废案

3D 场景重建（COLMAP+MiDaS · v0.11.1）

40 张车间连拍注册 38 张 + 单目深度 → 30 万点云 → 16 个新视角。3D 背景 + 真人抠像 = 400 帧；结果 fall mAP50=0.49（5/10）。

放弃：3D 背景版本的精度骤降（0.49 vs 照片合成 0.995）——脱离真实视角合成反而引入分布偏差。此条同时证明"场景 3D 不是刚需"。
废案

真人 3D 重建（v0.11.2，关键失败）

COLMAP 位姿 + MiDaS 深度 + 12 个"站立"视图掩码融合 → 点云包围盒 37m/10m 级（分时段仍 10m 级）。

硬性失败：数据集的人物是运动对象、没有静止多视角——**数学上无法从现有照片重建同一真人的 3D**。失败产物删除，结论写入 README/CHANGELOG。这是"照片→3D 建模"分支的终结判决。
废案

SMPL 真人 3D + Blender 全链路（v0.11.5-14）

单图拟合 SMPL + 照片纹理 + 场景点云，Blender 渲染 5 种摔倒关键帧（镜头保护/画幅校验/206 张重生成）；val mAP50=0.734 / test 0.755。

放弃：渲染结果"离真人还差得远"；精度不如 2D 像素合成（0.99 级）；工程链路最长（建模/烘焙/渲染每个环节都是坑）。调研同时给出方向判断："无限逼近真实只有生成式扩散能做到"。
废案

扩散生成真人（v0.11.16-22，实验）

全新扩散数据集，链路不依赖 YOLO；修"场景抠人残留人形模糊区" + 224 张新数据；pytest 21/21。

与 DSH 时代的 H3 方案同期并行的方向；最终以"扩散式生成视频"（H3 I2V）取代"扩散式生成图片再拼合"——首帧锚定让人物一致性从概率问题变成结构性保证。

① 视频生成主线

废案

动画片方案（SD1.5 + AnimateDiff-Evolved + Counterfeit）

用工坊的卡通动画引擎生成摔倒镜头，意在复用已有动画管线。

放弃原因：卡通画风与实拍数据集（车间照片）气质完全不符；合成数据的目的是补训练分布，风格漂移会引入系统性偏差。最终整体弃用。
废案

H3 纯文本生成（T2V）

不提供首帧，仅以文字描述摔倒过程。

放弃原因：无首帧锚定，人物外观、场景、机位在镜头内漂移严重；安全帽、服装、车间细节完全不受控，无法用于标注与训练。核心教训：人物一致性必须由"首帧"锁定，不能依赖提示词。
现役

H3 图生视频（I2V）+ 站立帧照片

真实照片 → 站起反推 → 导出站立帧 → 作为 I2V 首帧 → 生成摔倒过程。

为什么成功：首帧即"人物+场景"的地面真值；提示词只描述动作；（早期单帧）全数据集同一人同一景；（后期）10 张站立帧轮转兼顾多样性与每条内部一致性。这是所有废案淘汰后收敛的结果。
废案

官方多镜头参考（Ref2VA）

H3 官方参考图模式，用 3 张参考图跨镜头锁定人物身份，是官方"多镜头连续"标准答案。

放弃原因：参考编码器常驻显存；在 4GB 笔记本上实测中途崩溃，官方文档也注明该模式内存占用高。降级为：工坊侧用角色 LoRA 训练实现跨镜头一致（待实施）；数据集侧改用 I2V 单镜头方案，一致性已够用。

② 画布与画质演进

废案

448×256 / 512×288 画布

早期在低显存下"能跑"的尺寸。

放弃原因：细节不足——安全帽反光条、面部、格栅地面纹理在放大后糊；对"标注级"数据不达标准。迭代方式：先证明能跑（448）→ 提升到 512 看纹理 → 查官方低显存文档找到 640×352 验证桶 → 用"画质抽帧目测"逐档验收。
现役

640×352 官方低显存画布

h3lite 官方技能包中明确验证过的低显存画布（约 0.16MP），配合 W4A8 量化 + 块缓存 + 分块前馈在 4GB 上稳定。

为什么行：官方"验证桶"意味着采样器/VAE/缓存都在此尺寸被测试过；配合 6 步采样（质量与速度的平衡点）成为本机唯一可信画布。
现役

RIFE ×2 帧插值 → 48fps

H3 原生 24fps；用户要求≥30fps。引入 ComfyUI-Frame-Interpolation（RIFE49 模型 + taichi 后端）在解码后插值。

为什么行：插值对"合成数据"是安全的（没有真实物理刚体破绽）；48fps 满足且超出目标；全链路仅增加约 1 分钟/条。也有代价：模型放置目录是 vfi_models/rife/<hl>（按目录名推断，初版放错 RIFE_VFI 导致下载失败），配置 yaml 必须以纯 ASCII 写（GBK 读取会崩），均为实际踩坑。
现役

RealESRGAN ×4 → 1280×720

帧级超分到 720p；ncnn-vulkan 版（默认 -g 1 强制独显），失败时 ComfyUI 兜底。

为什么行：画布 640×352 超分到 720p 是官方推荐消费路径；逐帧超分在 4GB 上仍可行（单帧 ~1s）。痛点：ncnn 与 Comfy 抢 GPU 偶发失败（已有兜底）；观察记录在案。

③ 内容与构图设计

现役

固定机位 + 首帧锁定 + 全身优先取景

提示词固定"监控机位，构图与首帧一致"；取景加权（全身 70% / 轻微裁边 22% / 残缺 8%），因为用户明确"全身居多、残缺越多概率越低"。

为什么行：监控视角 = 真实验收场景视角；全身优先 = 标注框完整性；概率加权 = 数据分布可控。
现役

蹲姿分支（40% + 蹲→倒 55%）

新增"蹲下"独立类别：全程蹲=3（不算摔倒）；蹲后失衡倒地=2（摔倒）。提示词区分"蹲着检修"与"蹲久了失衡前扑"。

为什么加：真图检验发现"蹲着干活"被 3 类模型误判为摔倒（真实工业场景大量蹲姿作业）。解法不是修误判，而是给它独立类别——模型从此学会"蹲 ≠ 摔"。

④ 判定算法演进

废案

高度比判定（h < 0.92×站立高度）

用人体框高度下降程度划定"开始失衡"。

放弃原因：对轻微位移/蹲伏/镜头晃动全部误报——"失衡"阈值过低，数据全标成失衡。教训：框高度是"尺度"不是"姿态"，不能直接当姿态用。
废案

纵横比判定（h/w < 1.55 ≈ 45°）

用框宽高比近似人体倾斜角。

放弃原因：蹲姿天然低纵横比（比例≈1.0），站立前倾也常在 1.5 附近——纵横比在两个类别上不可区分；真正需要的是"躯干轴的倾角"而非"包络框形状"。
现役

姿态角判定（yolo11n-pose 关键点，45° 阈值）

取肩中点到髋中点连线与竖直线的夹角；z1=首次>45°（失衡，可回正），z2=>45°且后续保持>45°（不可回正=摔倒）；贴地帧关键点丢失按"持续"处理。

为什么行：姿态角是唯一在"站立/蹲姿/摔倒"三者上都能正确表述的物理量；45° 由用户目视标准定义。工程细节：检测从 GPU 挪到 CPU，再挪到 680M 核显（ONNX+DirectML），彻底避免与生成抢显存。

4GB 显存攻克专题

整个项目的最大约束。官方 H3 的推荐门槛是 8GB 起步；本机只有 4GB，且没有独立显存的富余。以下每一步都是在"跑不起来"与"跑得动但慢"之间反复试探出的解。

1

第一关：W4A8 量化 + 官方低显存加载器

把权重切成 4bit 激活 8bit（W4A8），用官方 ExperimentalW4A8UNETLoader 加载，配合 --lowvram 启动。这一步把模型本身"塞进"显存，是后面一切的前提。

2

第二关：MiniMaxH3BlockCache 块缓存

低显存模式下权重不能全驻显存，必须按块搬入搬出；块缓存让常用块留在显存，避免每步从头搬。K 与块数调参后，单步采样稳定在 65-70s。

3

第三关：ChunkFeedForward(chunks=6, min_tokens=4096) 分块前馈

前馈层整体算会瞬时爆显存；切成 6 块、每块最小 4096 token，逐块算——这是从尝试 4 块（仍爆）到 6 块（通过）的收敛过程。结果：0 OOM。

4

第四关：画布妥协与反击（448→512→640）

先降到 448×256 保证能跑；纹理糊 → 512×288；查官方 h3lite 技能确认 640×352 为验证桶并在 4GB 上实测通过。这是"先问官方再调参"的转折：花在试错上的时间远多于读文档。

5

第五关：帧率与分辨率的"绕行"

原生 24fps 不满足 30fps 目标、640×352 不满足 720p 目标——但两者都不能在生成侧提升（显存）。绕行方案：RIFE 插值到 48fps + RealESRGAN 帧级超分到 720p。把"生成做不到"变成"后处理能做到"。

6

第六关：生成与标注的分工

标注（姿态检测）一开始也在独显上跑，与 Comfy 生成互相抢卡导致死锁、队列堵死、单条从 10 分钟拖到 4 小时。解法：标注切 680M 核显（yolo11n-pose 导出 ONNX + DirectML），独显完全让给生成。这一关也是"稳定性工程"的根源部分。

7

第七关：采样与标注的取帧规则定型

标注取帧只取后半段（SAMPLE_FROM=0.5，每秒 8 帧）——因为前半段可能是"轻微失衡又回正"的假摔；只有后半段的持续失衡才是真摔的起点。这个规则是用户对"检测不能太早也不能太晚"的直接要求，最终固化为：前 35% 采负样本（0/3），后半段采正样本（1/2）。

标注体系演进

自动化是硬要求（用户：不做人工标注）。但自动化标注的"语义"才是难点——它要回答"什么时候算失衡、什么时候算摔倒"。

四类标签体系（现役）

类别含义判定用途
0 站立直立/轻微晃动，可回正躯干倾角 < 45°负样本（区分"没失衡"）
1 失衡倾斜 ≥45°，但仍可能回正倾角首次 >45°预警/中间态（让模型学会边界）
2 摔倒≥45° 且不可回正（必定摔）倾角 >45° 且后续保持 >45°检测触发目标
3 蹲下全程蹲姿作业（不算摔倒）蹲姿分支，未摔倒段消除"蹲≠摔"误判

演进过程（为什么是四类而不是一类）

① 最初只有"人框"（检测人）→ ② 二区（前段=0/后段=1，问题：误触发无负样本）→ ③ 三区（+失衡预警，问题：蹲姿无法表达）→ ④ 四区（+蹲下）。每一步都是被"真实数据暴露的错误"推着走的：先是"可回正踉跄"的误报，后是"蹲着干活"的误报。

标注管线

生成即标注（yolo11s-seg 每帧人框 + 多边形 seg）→ 姿态判定写入类别 → 自训练（yolo11s，四类，60 epochs / imgsz 512 / batch 8）→ 精修模型回填。像素级备选：SAM2.1 tiny 视频级传播（影子方案，未启用）。

人形识别原理（怎么识别出的人形）

标注的本质，是让程序替人回答这帧画面里的三件事：有没有人形？人形在哪？人是什么姿态？本项目的答案分四步——「先定位（检测出像人的区域）→ 再证明（关键点＋像素掩码确认这是完整的人）→ 后描态（躯干角度读出站立/失衡/摔倒/蹲）→ 兜底（识别失败宁可空着也不乱标）」。

底层原理：YOLO 为什么能「看见」人

YOLO 把画面切成 S×S 网格，每个网格输出一组候选（框中心/宽高/对象置信度/类别概率）；模型在 COCO 等大规模人像标注数据上训练出「人形」的统计特征——头肩结构、四肢比例、服装纹理、边缘轮廓的组合。推理时一次前向经过多尺度特征金字塔：每个网格预测候选 → 置信度 ≥0.25 过滤 → NMS 去重 → 得到「人」框；关键点分支再在框内预测 17 个关键点的位置与可见度（本项目收敛为 14 点：脖/额 + 肩肘腕髋膝踝×2）。这不是模板匹配，而是深度网络从海量样本里学到的「人形特征响应」。

项目识别链（怎么识别出人形）

第①步

人框定位：yolo11n-pose 优先

姿态模型只有「人」这一类，天然不被背景/窗户/杂物抢框；conf≥0.25，1920 主推定 → 1280 降档重试；多框时按「框置信 + 0.12×强关键点数」打分选主框（骨架弱的幻影框面积再大也不抢）；同一人物的碎框（IoU≥0.05）合并取外接。

兜底链：yolo11s-seg 分割掩码框 → yolo11n 检测框（仅 person 类）。
第②步

骨架证明：14 关键点只标真实检出

脖/额（由鼻/眼与双肩中点推得）+ 身体 12 点。conf≥0.5 → vis=2（强可见），0.15~0.5 → vis=1，越低越弱。越界（坐标不在画面内）一律不标；不做镜像脑补、不做解剖外推——上一版乱标点的主因就在这里被根治。

含义：关键点回答「这框里确实是人」，并给出姿态角原料。
第③步

像素级人形：分割掩码 + SAM2 精修

yolo11s-seg 只取 person 类最大面积掩码（防窗户/杂物大掩码抢框），且掩码必须与人物框指向同一目标（交并/较小面积 ≥0.4）才采用；掩码边缘简化 ≤100 点成多边形。

SAM2.1 tiny（框提示精修）仅在掩码漏点/贴边出画/过小时运行；提示框以「人体证据」（掩码∪关键点+12%）为界，面积守卫：SAM2 掩码 >2.5×原掩码或 >0.30 画面即拒用。
第④步

完全框选：掩码∪关键点 + 4% 边距

最终框 = [像素级掩码 ∪ 画面内可视关键点] 的并集＋4% 边距，再 clamp 到画面内——贴边人体（头盔顶/腿脚漏出框外）全部罩进框，这是「识别出的人形」的最终答案。

宁缺毋滥：黑帧（均值亮度<25）不标注；最终框 <1.5% 画面视为「没认出人」→ 不标注。
第⑤步

描态：躯干轴倾角 45° 阈值

髋中点→肩中点连线（躯干轴）与竖直线的夹角：首次 >45° = 失衡（z1，可回正）；>45° 且后续帧持续 >45° = 摔倒（z2，不可回正）；贴地丢关键点按「持续」处理；全程蹲姿 = 类别 3（蹲≠摔）。

关键点从「证明存在」升级为「读状态」——这就是四类标签（0 站立/1 失衡/2 摔倒/3 蹲下）的物理来源。

为什么是这套组合（而非单模型）

环节解决什么为什么用它
yolo11n-pose人框 + 骨架单一人类别，防背景抢框；骨架天然支持姿态角
yolo11s-seg像素级掩码贴边/出画肢体补全；多边形标注的直接来源
SAM2.1 tiny精修掩码分割漏点、贴边出画时的补全；面积守卫防幻影
yolo11n（检测兜底）最后防线pose/分割全失败时保底（仅 person 类）
ONNX + DirectML（680M 核显）算力29ms/帧且不与 H3 生成抢独显

一句话总结：Pose 负责「认出人」并给出姿态角，Seg/SAM2 负责「描出完整人形」，多级兜底与面积守卫负责「不认错」，角度判据负责「读出状态」——识别结果再回填自训练（yolo11n 四类 60 epochs），模型与标注闭环进化。
